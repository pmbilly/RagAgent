01-B产品介绍

本项目的验收标准不是「看起来对」，而是行为字节级一致：同一请求打到 Go 参考实现与 Java 实现两侧，响应体（JSON 键序、HTML 转义、SSE 帧格式、错误文案、时区渲染）必须逐字节相同。为此建立了 1,748 条 golden 契约实录与 72 个双端 A/B / 录制脚本；HTTP 路由面已全量翻译，程序化对账后唯一留白是 Go 工具路由 /swagger/{}（非翻译目标）。

为什么 WeKnora 上游持续演进，本项目以行为等价为对齐目标：功能对照以 Go 仓为参考实现，本仓文档描述 Java 侧的部署与使用。

01-C安装部署

前置：JDK 21（/opt/homebrew/opt/openjdk@21 或等效）、Docker、Node 20+。

# 1) 基础设施：postgres/ParadeDB(15432) + redis(16379) + docreader(50051)
#    与 Go 仓 dev 容器同端口，两套只能起一套（已有同端口容器时直接复用）
docker compose up -d

# 2) 密钥与连接配置（.env 已 gitignore，必需键见 scripts/dev-env.sh 头注释）
#    JWT_SECRET / SYSTEM_AES_KEY / DB_* / REDIS_* / LOCAL_STORAGE_BASE_DIR …

# 3) 后端（默认 :8082）
./gradlew bootRun
#    或带就绪等待：scripts/java-server-up.sh

# 4) 前端（:5173，代理显式指向 Java 后端）
cd frontend && npm ci
VITE_DEV_PROXY_TARGET=http://localhost:8082 npm run dev
注意 ParadeDB 镜像内含 pgvector 与 BM25 索引能力，是混合检索的依赖；换用普通 postgres 镜像会让向量与关键词检索退化为空。

02-B契约驱动的翻译方法

37 个领域包与 Go 仓 internal/* 存在系统性映射：handler → controller、application/service → service、application/repository → mapper、types → domain、models → llm、middleware/router → common/web + config/WebConfig。1:1 映射让每一批翻译都可审计——看 Java 文件名即知 Go 原文位置。

02-D文档入库流程

阶段行为
1 · 上传文件落存储后端，knowledge 行进入处理队列

02-E验收体系与回归纪律

全量测试按域分批执行（同一 JVM 跑全量会触发 Mockito self-attach 风暴）；Docker 集成测试由 WEKNORA_SANDBOX_DOCKER_IT=true 门控，覆盖容器执行面与产物排水全链（容器 → 收集器 → resource:// 注册 → 磁盘回环 → 去重与引用历史）。日常提交跑受影响批，交付门跑全量五批。

陷阱 跑 ./gradlew test 会重写 bootRun 正在使用的 build/classes——运行中的服务随即全站 500（NoClassDefFoundError），重启服务即解。
Docs / Agent 工作流

四类内置 Agent：一条固定管线，三个工具循环预设

四类 Agent 共享同一个入口与会话装配；分歧发生在装配之后——快速问答走固定的 RAG 插件管线，智能推理 / 维基问答 / 数据分析师共用同一个 ReAct 工具循环，靠预设的工具白名单与迭代预算分化。

内置角色 6 个（其中问答面 4 个） 入口 POST /api/v1/agent-chat/{id}

03-BSSE 帧序对照

同一句提问，两条路径回传的帧序不同——这是客户端（前端 / IM 渠道）必须知道的契约差异：快答路径没有 agent_query 与 thinking 帧，其进度以 tool_call / tool_result 帧承载阶段名（query_understand、knowledge_search）。

无 agent_query / 无 thinking tool_call(query_understand)tool_resulttool_call(knowledge_search)tool_resultanswercomplete
智能推理rag-qa
agent_querythinkingtool_calltool_result… ↻ 可多轮 …answercomplete
维基问答wiki-qa
agent_querythinkingtool_call(wiki_*)tool_resultanswercomplete

契约 错误帧为 error；产物挂载另有 artifacts_pending；工具输出流可有 command_output。以上帧序在双端 A/B 脚本中逐帧对拍。

选用指引

四个角色没有强弱之分，差别是适用边界——按「问题形态」选，而不是按「哪个更强」选。

快速问答

quick-answer
适用
单轮事实问答；答案在知识库里；对延迟敏感（固定检索链，无工具往返）。
别用
需要多步推理、跨工具编排——它没有工具循环可回旋。

智能推理

smart-reasoning · rag-qa
适用
需要多轮检索与推理：跨多个知识库、查图谱、反复核对引用。
别用
纯闲聊或单轮事实问答——固定管线更快、更省预算。

维基问答

smart-reasoning · wiki-qa
适用
知识库已开 wiki 能力；问题面向条目化知识，需要页级引用与源文档回溯。
别用
KB 未开 wiki（工具被门控）；或只需普通文档检索。

数据分析师

smart-reasoning · data-analysis
适用
会话附件或 KB 里有 CSV / Excel；需要统计、聚合与表格化结论。
别用
纯文本知识问答；对超大表做高频扫描（DuckDB 在会话内建内存表）。
